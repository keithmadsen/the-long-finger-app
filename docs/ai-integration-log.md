## 2. MCP Server Usage

The record documents three explicit MCP decisions, only one of which resulted in ongoing use — and it honestly notes the brief's suggested Postman MCP was replaced by something the team judged better.

- **Playwright MCP — used, then its output gitignored.** PR #18 (`chore/gitignore-playwright-mcp`, merged into `epic-2-retro-2026-07-01.md`'s PR list) added `.playwright-mcp/` to `.gitignore` with the comment "Playwright MCP scratch output (page snapshots from browser verification)". This is direct evidence the agent drove a real browser via the Playwright MCP server during Story 2.3's end-to-end delete verification (page snapshots, not committed test code) — separate from the *committed* Playwright test harness that came later (Story 3.4).
- **Chrome DevTools MCP — adopted, deliberately scoped to investigation only, never CI.** The epic-1 retro's tooling table records the decision explicitly: "🟡 Adopt as DX/investigation aid only... Agent-driven real-Chrome inspection (DOM, a11y tree, focus, network, perf) for authoring/debugging the delete Playwright specs and eyeballing deferred a11y states. Feeds the Playwright specs; **no CI role**, not a test layer." The epic-2 retro confirms it was actually used this way: "the real-browser arm→confirm→revert timing/focus behavior was verified once, manually (Playwright/Chrome DevTools MCP as an investigation aid)."
- **Postman MCP — declined; replaced by TypeBox contract enforcement at both boundaries.** The brief's suggested API-testing tool was explicitly evaluated and skipped. Epic-1 retro tooling table: "⚪ Skip for the automated strategy — The 6-endpoint API is already covered by 27 in-repo Vitest integration tests (real Fastify + real SQLite, in CI). A Postman collection would be a second, out-of-repo, drift-prone home for the same coverage (duplicate-coverage anti-pattern)." The substitution that was actually built and hardened over two epics is `@tlf/contracts` — shared TypeBox schemas validated at the API boundary (Ajv/Fastify) *and* at the web client boundary (`apps/web/src/api/validateContract.ts`), established as a cross-cutting fix in Story 2.1 after the shape-validation bug recurred four times in Epic 1 (see §3).
- **Pact (CDC) — also declined**, same retro table: "❌ Skip — This is a monorepo with a single atomic deployable... the contract is already shared code... Revisit only if the API is split into an independently-deployed service."
- **The record is silent** on which MCP servers, if any, were used during Epic 1's earlier stories (1.1–1.9) — no story file or retro before Story 2.3 mentions MCP tooling by name.
- **This document's own provenance is itself an MCP-adjacent data point:** it was reconstructed on branch `chore/instructions-gap-closure`, executed by AI agents coordinated per-task (see Provenance below) — the same pattern of agent-driven, human-supervised work the log otherwise describes.

## 4. Debugging with AI

- **npm-as-PID-1 SIGTERM diagnosis (Story 3.5).** The Dockerfile's own comment records the fix: `# Exec-form direct invocation so PID 1 is node itself (Story 3.5): npm as PID 1 / does not reliably forward SIGTERM, so \`docker stop\` used to wait the full 10s`. Story 3.5's Dev Notes spell out the diagnosis in full: "`index.ts` registers no signal handlers, and the container's `CMD ["npm", "run", "start", ...]` makes npm PID 1 — npm's signal forwarding is unreliable, so `docker stop` tends to hit the 10s timeout and SIGKILL." The fix was two-part: a `SIGTERM`/`SIGINT` handler in `index.ts` calling `app.close()` (which checkpoints the WAL via the awilix `db.close()` disposer), plus switching the Dockerfile `CMD` to exec-form `["node", "--import", "tsx", "apps/api/src/index.ts"]` so node itself is PID 1. The story's recorded verification: "`docker stop` took 0s (graceful path — pre-E2 this hit the 10s grace-period SIGKILL)."
- **A related regression caught in review of the same story:** the crash-recovery integration test's process-spawn shape was "corrected to single-process `node --import tsx` after tsx/cli wrapper form was caught passing vacuously" (`sprint-status.yaml`, 2026-07-14, 3-5 review line) — the original spawn form let the SIGKILL crash test pass without actually exercising the crash path.
- **TTI slow-3G budget miss (Story 3.4, Task 8).** A CDP network-emulation measurement (`e2e/load/measure-tti.mjs`, ~400ms latency / ~50KB/s down, matching DevTools' Slow-3G preset) against the built app recorded a median 7,839ms time-to-usable-list — against an original ≤1s budget that the story's own Dev Notes flag as "arithmetically unreachable" once the real bundle size and slow-3G math were worked through. Rather than silently picking a passing number, the story's task instructions explicitly required surfacing the conflict ("If the slow-3G math contradicts the original ≤1s budget, surface it to Keith; do not silently pick a number that hides the conflict"), which led to Keith approving a revised ≤10s budget during code review (a [Review][Patch] finding: "Revise the slow-3G performance budget and AC to ≤10 seconds with Keith's product approval").
- **Route-precedence leak in a new e2e spec** (Story 3.4 Debug Log): `interceptNetworkCall({url: '/todos'})` registered a `page.route` *after* an existing GET-scoping route; Playwright matches routes newest-first, so the later route's `route.continue()` bypassed the scoping filter and leaked another parallel worker's rows into a count assertion. Fixed by re-ordering route registration and syncing on the slow POST via `waitForResponse`.
- **Mid-transition axe false positive** (Story 3.4 Debug Log): the real-browser axe gate measured a contrast ratio of 4.26:1 on the armed-delete affordance — a color caught mid-`--motion-settle` CSS transition rather than the resting 6.6:1 state. Fixed by polling until the computed color matched the resolved token before scanning.
- **Coverage gate correctly went red, and the fix was more tests, not lower thresholds** (Story 3.4 Debug Log): the delete-path coverage gate failed at 84.6% against a 90% target on first run; closed by adding real tests for the tap-away guard branches and an unknown-id defensive fallback, landing at 97.59% statements / 92.3% branches.
- **Fastify v5 typing friction (Story 1.2 Debug Log):** `setErrorHandler`'s `error` callback param is typed `unknown` in Fastify v5; fixed by annotating it `FastifyError`. Separately, `@fastify/swagger` named schema components `def-0`/`def-1` instead of the registered `$id`s (`Todo`/`ErrorEnvelope`); fixed with a `refResolver.buildLocalReference` returning each schema's `$id`.

## 5. Limitations Encountered

Where the record shows a decision explicitly attributed to Keith rather than resolved by the agent, human judgment was the deciding factor — these are the load-bearing "Keith's call" lines in `sprint-status.yaml` and the story files, not paraphrase:

- **Declining whole-suite emulation Playwright projects.** `sprint-status.yaml`, 2026-07-14: "whole-suite emulation projects declined (Keith)." Story 3.4's Task 4 records the rationale to preserve: 3.3's per-test emulation gates already satisfied the WCAG criteria; running the entire UI suite again under emulation would multiply CI time with no new assertion coverage.
- **NVDA/VoiceOver manual smoke legs deferred to a release candidate.** `sprint-status.yaml`, 2026-07-09 (Story 3.2 review): "VoiceOver+NVDA smoke legs recorded as pending → release candidate (**Keith's call**)." Story 3.4's WCAG matrix records this honestly rather than papering over it: five WCAG criteria (2.1.1, 2.1.2, 2.4.3, 3.3.1, 3.3.4) are gated only by a scripted-but-not-yet-executed manual smoke test (`docs/screen-reader-smoke-test.md`), and the matrix doc "must state explicitly that the axe subset alone does NOT constitute 'AA enforced.'"
- **The k6 dual-track decision.** `sprint-status.yaml`, 2026-07-13: "scope locked with Keith: ... k6 dual-track (strict local container sign-off + loose CI tripwire)." This split — a strict formal sign-off run once against the local Docker container (`docs/k6-latency-signoff.md`, PASS at p50 2.85ms/p95 6.34ms) plus a separately-thresholded CI smoke job — exists because shared CI runners are too latency-noisy for the strict numbers to be a reliable per-PR gate, a call requiring product/infra judgment, not something the agent could derive from the k6 output alone.
- **Sequencing Story 3.5 ahead of 3.4.** `sprint-status.yaml`, 2026-07-14: "3-5 → ready-for-dev (create-story); created out of order — 3-4 remains backlog (**parallel track, Keith's call**)." A scheduling/priority decision, recorded rather than silently reordered.
- **The Epic 1 sizing observation.** The epic-1 retro's Key Insight — "a greenfield foundation epic will always be oversized; the mitigation is thin, dev-agent-sized stories, not a balanced story count" — is a planning judgment made by the human-and-agent team together in retro, not something derivable from any single story's code.
- **Story files routinely surfaced open questions rather than resolving them unilaterally.** Story 2.3's Dev Notes list four explicit "Open questions / scope confirmations for Keith (non-blocking — sensible defaults chosen)" — e.g. whether to reuse toggle's exact failure copy for delete, and whether to defer the LiveRegion re-announce fix. The agent proceeded with a stated default in each case but flagged the judgment call rather than treating its own choice as final.
- **Assistive-technology conformance ultimately requires a human with real AT**, not an automated proxy. The WCAG matrix (Story 3.4) is explicit that the axe-core/Playwright-emulation gates cover 10 of 15 enumerated 2.2 AA criteria; the remaining 5 require an actual NVDA/VoiceOver run, which as of this log's writing remains scheduled for the 3.5/release-candidate timeframe rather than completed.
