# Decision Log — Todo App / the long finger PRD

Canonical memory and audit trail for `docs/prd.md`. Bootstrapped 2026-06-15 by reverse-engineering the existing PRD, then extended with this session's update decisions.

## Bootstrapped decisions (reverse-engineered from PRD v1, 2026-05-24)

- **MVP is single-user, task-only.** No auth/multi-user (NG-1, NG-2); validate the Core Task Loop first. (§4)
- **Scope is CRUD-minus-edit.** Create, read, completion toggle, delete only. Description editing after create deferred (NG-7, FR-10). (§5.6)
- **Persistence behind a small API boundary** so future ownership fields can be added without replacing the app. (§4)
- **200-character description limit**, 1-char minimum, trimmed. (FR-3, §6)
- **Hard delete, no undo/archive/soft-delete** (NG-6, FR-6).
- **Four REST endpoints**: GET/POST /todos, PATCH/DELETE /todos/{id} (FR-10).
- **Original ordering assumption**: creation timestamp, newest first. *(Superseded 2026-06-15 — see below.)*
- **Six NFRs**: responsiveness, initial-load perf, accessibility (non-color completion cue), responsive layout 320px+, maintainability (separable layers), reliability (no data loss). (§7)

## Session 2026-06-15 — Update intent (architecture/UX ripple reconciliation)

Change signal: four amendments flagged by the architecture doc and UX spec that were never folded back into the PRD. User confirmed scope = these four only.

- **FR-5 / FR-1 — hybrid completed-item placement (APPLIED).** Completed items are visually de-emphasised in place during a session and sorted below active items on next page load. Canonical order: `completed` asc (false before true), then `updatedAt` desc. **Supersedes** the original "creation timestamp, newest first" ordering and **resolves Open Question #1**.
  - *Why:* UX spec Design Direction Decision 1 + architecture canonical-order query. Preserves "nothing moves unless the user moved it" within a session while solving long-session clutter at load.
- **FR-3 — visible vs. submit character limit (APPLIED, Option A).** Submit limit stays 200 chars; rendered list shows ~2 lines (~60–90 chars by viewport) with `…` truncation. Full description is persisted/submitted; truncation is a readability convention, not data loss.
  - *Why:* UX spec PRD Ripple 2; user chose Option A over tightening the limit to 100.
- **POST /todos — client-generated UUIDv7 + idempotent create (APPLIED).** POST accepts a client-generated UUIDv7 id in the body; backend validates format and treats creation as idempotent on that id. Enables optimistic create + safe retry.
  - *Why:* Architecture Data Architecture (ID strategy) + Important Gap #1 ratification request.
- **DELETE /todos/{id} — idempotent (APPLIED).** Returns success (204) whether or not a matching item existed.
  - *Why:* Architecture API contract + Important Gap #1 ratification request.
