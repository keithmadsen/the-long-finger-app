# BMAD Implementation Narrative

How the BMAD method actually shaped this project, reconstructed from its own written record — `_bmad-output/planning-artifacts/`, `_bmad-output/implementation-artifacts/`, and the story files. This is a synthesis of process and decisions; for tool/agent/model usage see [`docs/ai-integration-log.md`](./ai-integration-log.md).

## 1. Specs first

Nothing was built before the planning stack was validated end-to-end. The PRD went through a real iteration, not a rubber stamp: the first draft graded **Poor** — "not yet decision-ready," missing stable FR IDs and acceptance criteria (`_bmad-output/planning-artifacts/prds/prd-the-long-finger-2026-05-24/validation-report.md`) — and the revision one day later graded **Excellent** (`prds/prd-the-long-finger-2026-05-25/validation-report.md`). That PRD (`docs/prd.md`) then anchored the architecture (`_bmad-output/planning-artifacts/architecture.md`) and UX spec (`_bmad-output/planning-artifacts/ux-design-specification.md`), which in turn drove the epic/story breakdown (`_bmad-output/planning-artifacts/epics.md`, 3 epics / 19 stories). Before any code, the **implementation-readiness report** (`_bmad-output/planning-artifacts/implementation-readiness-report-2026-06-15.md`) checked all four documents for FR coverage (10/10, 100%), cross-document conflicts (the one real conflict — optimistic-UI vs. "honest-pending" — already resolved via architecture.md's 2026-06-15 amendment), and epic/story quality, and returned **READY** with zero critical or major findings. Implementation began 2026-06-16, the day after that gate closed.

## 2. Story-by-story build

Every story ran the same cycle: `create-story` → `dev-story` → code review → `done`, visible verbatim in `sprint-status.yaml`'s dated comment log. Story 1.2 (contracts/schema/repository) shows the cycle under real friction: dev-story complete → review (2026-06-17) → code-review found 2 issues → fixes applied → **second** review pass found more → final fixes applied → done (2026-06-18) — three "review" transitions before merge, each with regression tests added (`_bmad-output/implementation-artifacts/1-2-todo-contracts-schema-repository-real-read-path.md`, Change Log). 19 stories shipped across 3 epics from 2026-06-16 to 2026-07-14 (`sprint-status.yaml`).

Retros closed the loop between epics. The Epic 1 retro's action item 2 — "runtime contract-schema validation at every network boundary," prompted by the same shape-validation bug being independently re-discovered across four stories (1.1, 1.6, 1.7, 1.8) — was explicitly scoped to land in Story 2.1 (`epic-1-retro-2026-07-01.md`, Action Items), and `sprint-status.yaml`'s 2026-07-01 entry confirms it landed there ("runtime schema validation folded in per retro action item 2"); the Epic 2 retro's accountability table marks it "✅ Done." The Epic 2 retro likewise carried the committed Playwright e2e harness forward — action item 1, "a Story 3.3 prerequisite, owned by Story 3.4" (`epic-2-retro-2026-07-01.md`): the harness had to exist before 3.3's browser gates could run, and 3.4 owned delivering it — and `deferred-work.md` tracks it through to resolution: stood up 2026-07-04 (PR #20), consumed by Story 3.3's browser gates, and fully closed with the CI `e2e` job in Story 3.4 (2026-07-14).

## 3. Where we adapted BMAD

Three deliberate deviations from a straight-line process, each recorded rather than silent:

- **Code review in a fresh context, different model.** `sprint-status.yaml`'s own workflow notes prescribe it: "Dev moves story to 'review', then runs code-review (fresh context, different LLM recommended)" — an independent check, not a formality, per every story's multi-round Change Log (e.g. Story 1.2 above; Story 3.4's review resolved 11 findings).
- **Parallel-track stories when dependencies allowed.** Story 3-4 was created "in parallel with 3-3" (2026-07-13), and Story 3-5 was created "out of order — 3-4 remains backlog (parallel track, Keith's call)" on 2026-07-14 (`sprint-status.yaml`) — sequencing was relaxed once story dependencies genuinely permitted it, rather than forcing strict epic-order execution.
- **`deferred-work.md` as the pressure valve.** Rather than let stories grow to absorb every discovered gap, findings were named and routed to a specific future story — the nested-`<label>` DOM decision, the LiveRegion re-announce fix, the bundle-size ratchet rework — each entry later marked RESOLVED with the story and date that closed it (`_bmad-output/implementation-artifacts/deferred-work.md`). This is what kept Story 1.7-sized scope from ballooning: defer with a named target, don't drop and don't over-build now.

## 4. What the method bought us

Acceptance criteria are cited directly in code, not just in story files — e.g. `// AC 9` and `// Story 1.11 AC 4` in `apps/api/src/server.ts`, `AC 7` in `apps/api/src/types/cradle.ts` — so the traceability from PRD requirement to shipped line is inspectable, not asserted. Quality was built in from the first story: Story 1.1's walking skeleton shipped with a real on-disk SQLite read path and passing tests, not a stub to backfill later. And `sprint-status.yaml`'s dated comment log — every status transition, deferral, and retro decision in one file — is precisely what made this narrative reconstructable after the fact rather than requiring anyone's memory of how it went.
