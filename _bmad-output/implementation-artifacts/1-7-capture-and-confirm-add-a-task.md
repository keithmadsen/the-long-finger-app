# Story 1.7: Capture-and-confirm — add a task

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the Primary User,
I want to type a task into an always-present, always-focused input and press Enter to add it,
so that capturing a task is immediate and I'm never left wondering whether it saved.

## Acceptance Criteria

1. **Given** the list view, **When** it renders, **Then** the capture input is the **first interactive element in DOM order**, already focused, with a calm placeholder (`What do you want to do?`), and the empty-state instruction line "Type a task and press Enter to add it to your list." appears **above** it (and disappears after the first task is created). [Source: epics.md#Story-1.7; ux-design-specification.md (Step 7 §2.5 "First-interactive-element invariant"; Step 8 Empty State lines 613–619); UX-DR20]
2. **Given** the input has focus, **When** I press Enter on a non-empty, ≤200-char description, **Then** a `POST /todos` fires with a client-generated **UUIDv7** `id` **And** the input clears and refocuses **immediately on submit (not on confirm)** so I can type the next task. [Source: epics.md#Story-1.7; ux-design-specification.md Step 7 §2.2 lines 391–397; architecture.md#API-Communication-Patterns (POST contract); #Data-Architecture (UUIDv7 client-generated)]
3. **Given** an empty or whitespace-only input, **When** I press Enter, **Then** submission is silently suppressed; **Given** input reaching ≥180 chars, **Then** the `N/200` character counter appears (`--color-on-surface-muted`, `--font-size-micro`); over-200 is capped at the input via `maxLength`. [Source: epics.md#Story-1.7; ux-design-specification.md lines 1140, 1199–1200, 1284]
4. **Given** the honest-pending thresholds are driven by an **injectable clock (not wall-clock `setTimeout`)**, **When** a submit confirms **before** the flicker threshold fires, **Then** no pending visual is ever painted (the anti-flicker promise); **When** a submit confirms **after** the threshold fires, **Then** the pending treatment appears; **And** these boundaries are unit-tested with fake timers at the threshold edges. [Source: epics.md#Story-1.7; ux-design-specification.md lines 47, 347, 398, 638 (`--motion-none`); architecture.md#Frontend-Architecture (honest-pending, ~150ms flicker threshold)]
5. **Given** the pending treatment has become visible, **When** confirmation arrives shortly after, **Then** the pending treatment is held for at least the **minimum-hold floor** before settling (so it cannot flash-and-vanish) — the hold floor is clock-injectable and tested. [Source: epics.md#Story-1.7; ux-design-specification.md lines 47, 347, 398]
6. **Given** a pending row, **When** rendered, **Then** the pending treatment is a **muted-contrast shift ONLY**: no spinner, no shimmer, no italic, no position shift, no size or font-weight change; `aria-busy="true"` is set from **t=0** regardless of the visual delay. [Source: epics.md#Story-1.7; ux-design-specification.md "Pending State Visual Treatment" lines 486–494; lines 397, 443]
7. **Given** several tasks submitted in a burst, **When** they cross the threshold and resolve raggedly, **Then** each row settles **independently** on its own confirmation (no shared settle rhythm). [Source: epics.md#Story-1.7; ux-design-specification.md lines 274 (epics), 402]
8. **Given** the honest-pending pattern, **When** built, **Then** it defines the **reusable mutation-hook shape** (`onMutate` cancel→snapshot→pending cache write, `onError` rollback, `onSettled` invalidate `['todos']`) and the in-flight presentation contract, so toggle/delete consume it rather than re-derive it. [Source: epics.md#Story-1.7; architecture.md#Process-Patterns ("Honest-pending mutation flow (mandatory shape, all three mutations)"); #Enforcement-Guidelines; epics.md Notes A.1]
9. **Given** a task is confirmed, **When** it lands, **Then** the single page-wide `<LiveRegion>` announces **"{description} added."** (the submitted text is the disambiguator; pending→confirmed transitions generate no other announcement). [Source: epics.md#Story-1.7; ux-design-specification.md lines 350, 435, 443; UX-DR19]
10. **Given** several tasks submitted in rapid succession, **When** their requests are in flight, **Then** each pending item is **independent** (one's outcome does not affect another) — covered by an integration + e2e concurrent-submit test (writes are serialized + idempotent-on-id; no AC claims parallel backend execution). [Source: epics.md#Story-1.7; ux-design-specification.md line 402; architecture.md#Enforcement-Guidelines ("Per-row in-flight mutation arbitration … the synchronous better-sqlite3 backend is intentionally ignorant of it")]
11. **Given** a `POST /todos` whose client-generated UUIDv7 `id` already exists (e.g. a retry after timeout), **When** the server handles it, **Then** it returns **200 with the existing `Todo`** (no duplicate row, not an error) — covered by an explicit duplicate-id integration test, so the Story 1.9 Retry path is safe. [Source: epics.md#Story-1.7; architecture.md#API-Communication-Patterns; #Enforcement-Guidelines ("POST /todos idempotency: … returns 200 with the existing Todo")]
12. **Given** a successful create, **When** it settles, **Then** the settle is driven by `onSettled` invalidating `['todos']` — **NOT** by merging the `POST` 201 response body into the cache (the client already owns the final id; no reconciliation path is introduced). [Source: epics.md#Story-1.7; architecture.md#Process-Patterns; #Decision-Impact (client-generated id ⇒ no temporary-id reconciliation)]
13. **Given** two creates submitted concurrently where one fails and one succeeds, **When** both resolve, **Then** the success settles without clearing the other's error **And** the failure rolls back only its own row — a mixed-outcome concurrent test asserts no cross-contamination of the shared `['todos']` cache. [Source: epics.md#Story-1.7; ux-design-specification.md line 402; architecture.md#Communication-Patterns (immutable cache updates, `setQueryData` new references)]
14. **Given** the user has already created at least one task, **When** the list later returns to empty, **Then** the instruction line does **NOT** reappear (only the persistent "Your list will appear here." state line shows); **And** when the instruction line is removed after the first task, it **fades via `--motion-settle`** rather than vanishing abruptly. [Source: epics.md#Story-1.7; ux-design-specification.md lines 603 (instruction-line disappearance), 619]
15. **Given** the list view with the input, **When** CI runs, **Then** the **first-interactive-element invariant assertion** passes and is re-checked on changes that add interactive elements. [Source: epics.md#Story-1.7; ux-design-specification.md line 387]
16. **Given** the pending state now exists (its only consumer), **When** the contrast gate runs, **Then** the **pending-vs-settled distinction is enforced at the documented ≥3:1 target** and the color-system contradiction deferred from Story 1.6 is resolved (no gate threshold is silently weaker than the spec). [Source: deferred-work.md (2026-06-20); 1-6…md Review Findings (deferred) + Completion Notes; ux-design-specification.md Contrast verification line 484; #Pending-State-Visual-Treatment]

### Architecture Compliance (guardrails)

- **Honest-pending is mandatory and load-bearing** (UX-DR15; architecture amendment 2026-06-15). Render the in-flight item as **pending, not as done**: `aria-busy="true"` at t=0, visual cue delayed to ~150ms, rollback on error. This is NOT optimistic UI — never show an unconfirmed item as confirmed. The trust thesis depends on it; any departure is a PRD revision, not an engineering shortcut. [Source: architecture.md frontmatter amendmentNote; #Frontend-Architecture; ux-design-specification.md lines 316, 363]
- **Mandatory mutation flow shape** (identical for create/toggle/delete): `onMutate` cancel→snapshot→**pending** cache write → `onError` rollback → `onSettled` invalidate `['todos']`. Client generates the UUIDv7 so the pending row already carries its final id (no temp-id reconciliation). This story DEFINES the shape; 1.8/1.9/Epic 2 reuse it. [Source: architecture.md#Process-Patterns; #Enforcement-Guidelines]
- **Settle = invalidate, not merge** (AC 12): the 201 body is not written into the cache; `onSettled` invalidation refetch is the canonical settle. [Source: architecture.md#Decision-Impact]
- **Component boundary:** primitives (data-agnostic) → recipes (compose primitives) → hooks (the only network touch, via `api/todos.ts`). State flows down via props, mutations up via hooks. CaptureInput is a recipe; `useCreateTodo` is a hook. [Source: architecture.md#Component-boundary]
- **Backend clean-architecture:** the `clean-architecture` skill is authoritative — consult it before writing the handler. Handlers stay thin (orchestration + status mapping); repositories do data access only; the 201/200 decision is handler/route orchestration; timestamps are repository-stamped; casing stays in the mapper. No `create`-prefix on factory names. [Source: architecture.md#Enforcement-Guidelines; #Naming-Patterns]
- **Backend is synchronous and ignorant of per-row arbitration** — concurrency correctness (idempotent-on-id + serialized writes) is backend; per-row in-flight arbitration is frontend hooks + `<TodoItem>`. No backend code claims parallel execution. [Source: architecture.md#Enforcement-Guidelines]
- **Immutable cache updates only** — never mutate query cache objects; `setQueryData` with new references. [Source: architecture.md#Communication-Patterns]

### Pending-state visual contract (precise)

A pending create row is **muted-contrast shift ONLY** (the new `--color-pending` replacing `--color-on-surface`): no spinner, no shimmer, no italic, no position/size/font-weight change. `aria-busy="true"` from t=0; visual cue gated by the flicker threshold + min-hold. Pending→settled colour shift via `--motion-settle` (reduced-motion → instant). Under `prefers-contrast: more`, visual distinction collapses to `--color-on-surface` and `aria-busy` carries the signal alone. For SR users: silent-until-confirmed (busy at t=0, "added" on confirm) — auditory parity with the visual "appears instant / honest pending." [Source: ux-design-specification.md lines 486–494, 443]

### Latest Technical Information (verified 2026-06-22)

- **`uuid` v14.0.0** is the latest (released April 2026) and exports the v7 generator: `import { v7 as uuidv7 } from 'uuid'`. Pin `^14.0.0`. Native `crypto.randomUUID()` is v4-only and cannot satisfy the time-sortable client-id requirement. [Source: npmjs.com/package/uuid; web research 2026-06-22]
- **TanStack Query v5** (`^5.101.0`, already installed) — `useMutation` `onMutate`/`onError`/`onSettled` lifecycle is the standard optimistic-update shape; here it carries a *pending* (not done) cache write. `queryClient.cancelQueries`/`getQueryData`/`setQueryData`/`invalidateQueries` keyed by `['todos']`. [Source: tanstack.com/query/v5; architecture.md]
